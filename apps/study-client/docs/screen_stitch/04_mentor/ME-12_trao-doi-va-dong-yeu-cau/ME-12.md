## A. Tổng quan màn hình

### A.1. Mục tiêu và phạm vi

ME-12 is the Mentor detail page for one support request. The intended page reads a request thread, lets the Mentor send a reply, and lets the Mentor resolve the request after the learner is satisfied and the current lifecycle state permits resolution. The page is entered from ME-11 with the selected request ID.

The current PNG/HTML only shows the initial empty-thread composition. It contains a loading request-ID placeholder, a static OPEN-looking status, a blank reply box and disabled actions. It does not define how a loaded message thread, attachment preview, message author/time, success state, error state, confirmation prompt, or long thread is laid out. Those states remain design decisions.

### A.2. Actor, preconditions and postconditions

| Item | Specification |
|---|---|
| Actor | Authenticated Mentor whose identity owns the course linked to the request. API source checks Mentor role and direct course ownership against the JWT subject. |
| Preconditions | Expected route has requestId from ME-11 #58 data[].id. Request exists, is in the Mentor's course scope, and the Mentor session is valid. Exact route implementation and session integration do not exist in Study Web. |
| Read postcondition | Request metadata and full ordered message thread are available from #59, or a mapped error/empty-message state is shown. A valid request may have messages: []. |
| Reply postcondition | #60 inserts one message and any permitted attachment links atomically. The API returns the full updated request. Status is preserved by current source. |
| Resolve postcondition | #61 changes an allowed active state to RESOLVED and returns the full request. Repeating resolve on RESOLVED is idempotent in current source. |
| Screen exit | Back action is intended to return to ME-11. Other menu/footer destinations have no confirmed route in the prototype. |

### A.3. Route and screen relationships

- Expected inbound flow: ME-11 calls #58 and passes numeric SupportRequest id from data[].id to /mentor/support/:requestId.
- Expected current-screen flow: route requestId → GET #59 → render detail/thread → POST #60 when reply is permitted → refresh #59 per inventory → PATCH #61 when resolve is permitted.
- Expected return: back button → /mentor/support (ME-11). List-filter restoration is unspecified.
- No Student create-request route/API is present in this flow. Do not add a create-request action from ME-12 or a Student CTA based on this page.
- The static code.html uses href="#" for header, breadcrumb, back, help and footer anchors. It contains no app router binding or API client.

### A.4. Business rules and security

1. The Mentor must have an authenticated Mentor role. Each API checks ownership through the linked course and Mentor identity; UI state is not an authorization boundary.
2. Never trust a request ID or displayed status from the browser. Load from #59 and use server response for state and owner-scoped data.
3. #59 returns the complete thread, ordered by message created_at ascending with id as a tie-break; attachments are ordered by asset_position. The response is unpaginated.
4. #60 requires both message and attachment_refs. attachment_refs is a string containing a JSON array of unique signed int64 upload IDs; the string "[]" means no attachments. Existing UI has no attachment picker.
5. #60 rejects whitespace-only messages but has no source-level maximum length. The screenshot's 2000-character value is not an API rule.
6. #60 currently accepts replies for RESOLVED or CANCELLED requests and preserves their status. Whether the product should allow that remains unapproved.
7. #61 currently resolves OPEN, IN_PROGRESS and WAITING_LEARNER; a RESOLVED retry succeeds without another update; CANCELLED and other unsupported statuses return 422. #61 does not enforce a minimum message count or learner satisfaction.
8. Do not treat Socket/TLS 1.3, 24-hour SLA, automatic settlement, post-resolution satisfaction survey, privacy/source standards or WCAG footer copy as verified product behavior. The APIs do not return or enforce these claims.

## B. Mô tả luồng hoạt động tổng thể

### B.1. Entry and read

1. The user selects a support request in ME-11. Expected handoff is the numeric data[].id from #58. The current static ME-11/ME-12 assets do not execute this navigation.
2. A future route reads requestId and obtains the Mentor session through the shared application auth boundary. If route ID is absent or malformed, do not call the API. The exact redirect/session-expiry behavior awaits a Study Web router/auth implementation.
3. On route entry, show the loading state and call GET #59 once with the requestId and Authorization: Bearer token. The API has no query parameters or body. X-Trace-Id is optional when supplied by middleware/client policy.
4. On 200, validate/map the single SupportRequest object in data. Use returned id, course_id, student, status, created_at, resolved_at and messages. Do not derive status, course name, SLA, survey state, socket status or resolution reason from client assumptions.
5. Render messages in response order. For each message use id, author summary, content, attachments and created_at. For each attachment use only returned UploadAsset metadata (id, name, url, content_type, size_bytes, status); do not expose an unreturned storage path or infer a downloadable URL.
6. messages: [] is a valid empty thread for an existing request. This differs from request not found and from the inventory/AC precondition that a request exists.
7. A 401 follows the shared session-expiry behavior once that exists; 403 and 404 must not render another Mentor's request data; 500/network errors enter an error state. Retry should be user initiated unless a shared client policy is later documented.

### B.2. Reply

1. The Mentor enters a message. Preserve the draft locally while the page remains open. The prototype shows 0 / 2000, but API #60 has no maximum; do not enforce a hard-coded maximum as an accepted rule until approved.
2. Before submit, reject whitespace-only content as #60 does. Keep the original message text for the request because source validation strips only to test emptiness and stores the provided text.
3. Build the strict JSON body with message and attachment_refs. In the current UI there is no attachment picker, so the only source-supported no-attachment value is the JSON string "[]". Do not send an array in place of the required string.
4. POST #60 once. Disable the submit control during the in-flight request to limit accidental double clicks. The API has no idempotency key; never automatically retry a POST after an ambiguous transport failure.
5. On 200 DESIGN_RESOURCE_UPDATED, treat the returned full SupportRequest as evidence that the reply was committed. Then perform the inventory-required GET #59 refresh. If refresh fails after the POST succeeded, keep the success result and show a stale-refresh condition when a confirmed UI pattern exists; do not resend the reply.
6. Map #60 401/403/404/422/500 distinctly by business code. Preserve the draft on validation/network failure unless a product-approved retention rule says otherwise. Exact messages/toast/modal are not present in the asset.

### B.3. Resolve

1. The screenshot's resolve button is disabled and says it unlocks after one valid exchange. The #61 API does not enforce that minimum, and AC-24 describes the satisfied/unsatisfied decision without defining a confirmation component.
2. Until BA/BE confirms the gate and confirmation interaction, keep resolve blocked in implementation. A future allowed action sends PATCH #61 with requestId, Mentor Bearer authorization and no body/query.
3. On 200 DESIGN_RESOURCE_UPDATED, map returned status and resolved_at. Source transitions OPEN, IN_PROGRESS or WAITING_LEARNER to RESOLVED. A RESOLVED retry is idempotent. A CANCELLED or unsupported state returns 422 STATE_NOT_RESOLVABLE.
4. #61 already returns the full SupportRequest; whether to issue an additional GET after resolve is not specified in inventory and must be decided consistently with cache policy.
5. Do not claim automatic settlement or survey delivery from resolve success. Neither behavior is represented by #61 response or side effects.

### B.4. Exit and exceptions

- Back to list returns to the ME-11 route when navigation is implemented. Do not fabricate restored filters, list query state or a list refresh policy.
- Route deep-link/refresh behavior requires the same Mentor auth guard and a new #59 read; a client-cached thread is not an authorization substitute.
- #59 path parsing differs from #60/#61: invalid/out-of-range ID maps to 404 for #59 and 422 for #60/#61. #58 list model uses positive Int64 IDs; #59–#61 local path parsers accept signed int64 syntax and rely on lookup for absent/nonpositive IDs.
- For #60, framework body-model validation can return 422 before the route/view authentication guard is reached. Do not assume auth error always takes precedence for malformed body.
- No API in this screen establishes WebSocket connection, message push/reconnect behavior, SLA clock, file upload, payment settlement, survey, or source-guide destination.

## D. Đặc tả chi tiết sự kiện

### D.1. Shared API envelope and error handling

API success envelopes expose success, businessCode, message, data, meta and traceId. For #59–#61, success data is one SupportRequest object. Use the API-returned businessCode and HTTP status; do not infer success from HTTP status alone. Optional null fields may be omitted by response serialization.

| Response field | Type/meaning | UI mapping |
|---|---|---|
| success, businessCode, message, meta, traceId | Envelope fields; success is boolean, businessCode/message are strings, meta is an object, traceId is a string. | Check success and businessCode; retain traceId for diagnostics according to shared logging policy, without logging message content. |
| data.id | Positive int64 SupportRequest identifier in the response model. | Must equal route requestId; mismatch is a projection error. |
| data.course_id | Positive int64 course identifier. | No course title/slug is returned by #59–#61; do not derive a label. |
| data.student | User summary with id:int64, full_name:string and optional avatar_url:string. | Render only where the approved thread header needs student identity; privacy/display policy remains open. |
| data.status | String status. | Map only confirmed values; #61 local lifecycle includes OPEN, IN_PROGRESS, WAITING_LEARNER, RESOLVED, CANCELLED. |
| data.messages[] | Ordered message array; each item has id:int64, author summary, content:string, attachments array and created_at:datetime. | Render in server order; no pagination metadata is returned. |
| message.author | User summary with id, full_name and optional avatar_url. | Message author/time layout is not present in source mockup. |
| message.attachments[] | UploadAsset response items with id, name, url, content_type, size_bytes and status. | Render only returned metadata and link; attachment UI and file safety/download policy remain open. |
| data.created_at / data.resolved_at | Request creation datetime; optional resolution datetime (null fields can be omitted). | Display format/time zone is not defined by this screen source. |

### E01 — Load request detail

- **Trigger:** Route entry, refresh/deep link, or an explicit future user-initiated retry.
- **Elements:** Screen-level load; #15 request ID, #16 status, #19–#22 conversation/empty state.
- **Inputs:** requestId from route, Mentor access token, optional X-Trace-Id. No body/query. Expected ME-11 handoff is #58 data[].id. API path uses request_id.
- **Preconditions:** Mentor session is available; route ID parses to the expected request key. Local APIs use signed int64 path parsing. #59 returns 404 for invalid/out-of-range ID; a valid but absent ID returns 404. Do not call with missing route data.
- **Processing:** (1) Enter loading state. (2) Send GET /api/v1/mentor/support/{request_id} with Authorization: Bearer token and optional X-Trace-Id. (3) API authenticates Mentor before path parse/DB, checks request and course ownership, reads the full thread and ordered attachment projections. (4) On 200 DESIGN_RESOURCE_RETRIEVED, validate data as one SupportRequest and verify response id matches route requestId. (5) Map status/student/timestamps/messages/attachments. (6) If messages is empty, show the approved empty-thread state; if nonempty, render a loaded-thread design only after layout is approved. (7) Leave operation state idle.
- **Success output:** One mapped request. #59 has no commit; the API reads request/course/student and full message/attachment data. Response order is created_at ASC NULLS FIRST then id ASC; attachment links are ordered by asset_position. No pagination or cursor.
- **Errors:** 401 shared session flow; 403 owner-scope denied; 404 absent or invalid request; 500 query/projection failure. Network failure is a client transport condition, not an API business code. Keep error state distinct from messages:[].
- **Retry/cache:** No automatic retry is specified. User retry repeats GET. Do not cache data across owner/session changes without shared auth cache policy.
- **Trace:** inventory row ME-12 and F09; API #59 route/module/query/view/models; API #59 test and Draft DD; AC-24 precondition.

### E04 — Send reply

- **Trigger:** Submit/click #27.
- **Inputs:** requestId; Mentor Bearer token; message string; attachment_refs string. Current screen has no file picker, so use "[]" to represent an empty attachment list if the API is approved for this screen.
- **Preconditions:** Valid loaded request, valid Mentor session/ownership, non-whitespace message, approved status policy, no reply request currently in flight. Do not assume a maximum from the static counter.
- **Request:** POST /api/v1/mentor/support/{request_id}/reply; Content-Type application/json; Authorization: Bearer token; optional X-Trace-Id. Body has exactly message and attachment_refs. attachment_refs is a JSON-encoded string array of unique signed int64 UploadAsset IDs; empty list is serialized as the string "[]". Extra body fields are forbidden.
- **Processing:** (1) Keep original message text but reject trim-empty. (2) Serialize refs exactly once. (3) Send POST once and disable duplicate click while in flight. (4) Backend auth checks Mentor, parses path, locks request, verifies course owner and every upload is owned by the Mentor/course with purpose LECTURE and status UPLOADED. (5) Backend inserts support_messages and ordered upload links in one transaction. (6) Backend rehydrates/validates full SupportRequest response and commits once. (7) On 200 DESIGN_RESOURCE_UPDATED, map returned request as proof of successful post. (8) Perform the inventory-required GET #59 refresh. Do not repeat POST because the subsequent GET failed.

Keep draft after safe failure if confirmed by UX policy.

### E05 — Resolve support request

Whether at least one exchange is required and how learner satisfaction is confirmed are unresolved.
- **Processing:** (1) Confirm user intent only through a BA-approved UI interaction; do not invent a modal. (3) Backend authenticates, parses signed int64, locks the request, verifies ownership, and checks lifecycle.
