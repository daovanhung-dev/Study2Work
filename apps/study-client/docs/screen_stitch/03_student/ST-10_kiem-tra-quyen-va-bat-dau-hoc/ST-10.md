### Discrepancies cần giữ rõ

1. Asset hiển thị STATUS: 423_LOCKED. API catalog #22–#24 không khai báo HTTP 423 hoặc business code tương ứng; đây là static copy, không phải API response.
2. API #22 kiểm tra access nhưng success schema là ApiEnvelope<Lesson>, không có access boolean; AC-14 nói nhánh deny trả 403 “+ lý do”, nhưng catalog/envelope chưa quy định field reason. HTTP 200/403 cho phép phân nhánh theo status ở mức thiết kế, song predicate và reason chưa chốt.
3. AC-14 mô tả #23 UPSERT lesson_progress sang IN_PROGRESS; catalog #23 trả 201 Created và ApiEnvelope<Lesson>. Key, repeated-start semantics, field preservation, idempotency, response assembly và direct-call authorization còn mở.
4. #23 generic Lesson response có thể gồm content/video_url theo reusable schema; chưa có quyết định xác nhận payload nào được trả ở bước start.
5. #24 trả ApiEnvelope<Lesson>, với content/video_url optional trong catalog; API chưa có current implementation để xác nhận authorization, publication checks hoặc null serialization.
6. ST-09 source hiện không có lesson card/selection và CTA không có lessonId; vì vậy flow tới ST-10 thiếu đầu vào trong bộ screen design hiện có.
7. HTML nói “Session Token”, “giải phóng media” và “khóa vĩnh viễn” nhưng API catalog/DD không khai báo token/media grant hoặc trạng thái khóa vĩnh viễn.

## B. Mô tả luồng hoạt động tổng thể

### Expected flow theo AC-14/15 và inventory

1. Student vào route ST-10 với lessonId được chọn từ ST-09. Route, session guard và ID handoff chưa được nối trong Study Web; ST-09 asset hiện thiếu lesson selection.
2. Yêu cầu Student Bearer JWT theo catalog. Mỗi endpoint phải tự thực thi authorization phía server; việc client gọi #22 trước không thay thế kiểm tra quyền cho một request #23 hoặc #24 độc lập.
3. Gọi GET #22 để kiểm tra quyền lesson. AC-14 nêu enrollment/prerequisite check. Theo flow inventory, nhánh success/allowed mới đi tiếp; nhánh denied không gọi #24 và không tải/phát media. Response status 403 được khai báo, nhưng predicate và reason payload chưa được chốt. Success body ApiEnvelope<Lesson> không có access field riêng.
4. Chỉ sau khi access được chấp thuận, gọi POST #23 để ghi nhận bắt đầu. AC-14 ghi UPSERT lesson_progress với trạng thái IN_PROGRESS; inventory mong chống gửi lặp. Catalog chỉ nói POST, path lesson_id và HTTP 201 ApiEnvelope<Lesson>; semantics khi row đã tồn tại, khóa idempotency, cột cập nhật và retry chưa có quyết định.
5. Sau khi #23 thành công theo contract được duyệt, gọi GET #24 để lấy nội dung. AC-15 yêu cầu quyền xem và kiểm tra publish status, nhưng chưa chốt lesson/course gate hoặc query. Chỉ render content/video khi response #24 được backend xác nhận đã được phép; không lấy media từ #09 public curriculum hoặc từ response #22/#23 theo suy đoán.
6. Nếu #24 trả success, chuyển tới ST-11 với lessonId theo route inventory. Không có client router/runtime để xác minh history, session carry-over hoặc state transfer. ST-11 dự kiến gọi #24 khi vào player, nên việc #24 bị gọi ở cả ST-10 và ST-11 cần Product/FE xác nhận để tránh tải trùng; inventory hiện mô tả cả hai bước.
7. Khi access denied, start/content lỗi, session hết hạn, lesson không tồn tại hoặc mạng lỗi, UI cần state/mapping rõ. Asset chỉ vẽ ba FSM labels tĩnh; không có loading/error/timeout/retry handler hay API call thật.

Mô hình identity/field khác nhau; không suy ra API #23 conflict key, write mapping hoặc transaction từ một trong hai.

### Security rules for this screen

- Treat client order as UX orchestration only. Every protected server endpoint must own its authorization decision; direct calls to #23/#24 cannot rely on prior browser call to #22.
- Do not request/render content or video before the backend content endpoint confirms authorization. Do not copy public #09 fields into the protected flow.
- Current #09 itself is public and returns `content`/`video_url` for published lessons without checking enrollment. That current behavior is distinct from the missing #24 contract and requires a separate product/security decision if these fields are intended to be protected.
- Do not treat static SECURITY_GATE_ENFORCED, disabled button, 423_LOCKED, “Active” badge, bar width or Session Token copy as enforcement evidence.
- Do not assert that API #23 returns a media token: catalog type is Lesson, and no token field is declared.
- API #22 status 403 is catalogued, but its reason field/value/message is not. Do not create a reason enum or error body.
- Keep 403 vs 404 behavior, hiding of unpublished resources, enrollment status and prerequisite policy open until Product/Backend/security approve them.
- DDL and fake/test artifacts do not prove live schema. Do not build an upsert key or query from candidate DDL alone.

### Required decisions

1. #22 access predicate: eligible enrollment states, prerequisite model/order, JWT claim binding, allow signal, 403 reason field/type and 404 condition.
2. #23 progress upsert schema/identity and key: reconcile BIGINT `lesson_progress(user_id,lesson_id)` without composite unique against V1-PILOT UUID `lesson_progress_facts(enrollment_id,lesson_id)` with a unique pair; then decide fields updated/preserved, repeated-call and HTTP 201 semantics, idempotency/retry, transaction and direct-call authorization.
3. #24 server-side entitlement for independent calls; lesson and parent-course publish policy; 403/404 visibility; query/projection; content/video_url access and null serialization; LessonStatus enum; checked schema/nullability.
4. Resolve whether #23 response Lesson can include content/video_url before the separate #24 read.
5. ST-09 lesson-selection/lessonId source and ST-11 route/fetch ownership.
6. Error/loading/denied/failure UI and retry policy; no 423 mapping without catalog update.
7. Chốt trigger của #23 sau #22 allowed: auto-start theo sequence hay chờ thao tác Start; đồng thời chốt enabled state của #13.
8. Remove/approve static claims about “Session Token”, “permanent lock”, 423 and WCAG 2.1 AA; confirm Study design tokens and responsive/navigation behavior.
