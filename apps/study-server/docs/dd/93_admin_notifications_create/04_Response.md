## Structural success example

Angle-bracket values are explanatory placeholders, not accepted literal values.

~~~json
{
  "success": true,
  "businessCode": "DESIGN_OPERATION_ACCEPTED",
  "message": "<message unspecified>",
  "data": {
    "id": 123,
    "title": "Thông báo minh họa",
    "content": "Nội dung minh họa",
    "channels": ["PUSH", "EMAIL"],
    "status": "QUEUED",
    "created_at": "<ISO-8601 date-time>"
  },
  "meta": {
    "operation_id": "<UUID chung cho batch>",
    "notification_ids": [123, 124]
  },
  "traceId": "<trace identifier>"
}
~~~

## Response discrepancy and local fallback

- Catalog row and diagram say ApiEnvelope<Notification> with int64 Notification ID.
- Operation tracking summary says data: Operation with UUID Operation ID.
- The operation-status node is separate and has no edge from create.
- Local fallback keeps the endpoint-specific `ApiEnvelope<Notification>` and puts batch IDs/UUID in `meta`; this is not an approved Operation bridge. `data` is the first per-recipient row.
- 202 is returned only after all notification and delivery rows commit; it does not mean provider delivery succeeded.
- See [Q-93-01](./OPEN_QUESTIONS.md#q-93-01-notification-or-operation-response).
